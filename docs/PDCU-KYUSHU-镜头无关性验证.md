# PDCU「KYUSHU」与镜头、模式的关系——当前证据与未决点

日期：2026-10-23
对象：PDCU 5.10.2.2（四季菜单补丁版）
样本：`sample/IMGP1157.DNG`（HD FA 43）、`sample/IMGP1194.DNG`（FA 77）、两张 PNG、PDCU 导出 JPEG

> 维护者已确认：**`HDFA43_KYUSHU_IMGP1157.png` 的斜四边形才是正确的 KYUSHU**。
> 本文按这个前提重新整理证据，并标出还没锁死的地方。

---

## 1. 已确认的事实

### 1.1 镜头不参与调色

同一张 `IMGP1157.DNG`，只把 PentaxDng `LensType` 从 `4 3`（FA 43）改成 `4 18`（FA 77），
其余字节不动：

| 指标 | 结果 |
|---|---|
| 图像区平均绝对差 | **0.071 / 255** |
| 明显差异像素 | 0.065% |
| 雷达图 | **完全相同** |

之前对 `IMGP1194.DNG` 做 77→43、以及对 168 字节 `LensInfo` 做整块替换，结果同样是一致。
**镜头标识不进入颜色/色调计算；它只影响菜单里是否出现某个模式。**

### 1.2 同一张 1157，换模式号会换一张脸

只改 PentaxDng `ImageTone`（私有 IFD tag `0x004f`，文件偏移 `0x586`）：

| `ImageTone` | 雷达图形状 | 面板 |
|---|---|---|
| 12（相机原始值） | 五边形 | 高光/阴影滑块可用 |
| 15（PDCU 导出 JPEG 里的值） | 五边形 | —— |
| 31（0x1F，补丁菜单 KYUSHU 的内部值） | 六边形 | 高光/阴影滑块被禁用 |
| 8（Bleach Bypass） | 小菱形 | 本色/红色下拉 |
| 13 | 整幅洋红（无效） | —— |

同一文件在 12 与 31 之间的图像区平均差约 **10.4/255**（96% 像素不同）。

### 1.3 维护者的「正确」斜四边形，目前还没在确定性状态下复现

- `ImageTone=12`（直接打开）：五边形，不是斜四边形；
- `ImageTone=15`：五边形；
- `ImageTone=31`：六边形；
- `ImageTone=8`：小菱形；
- 维护者的 PNG：**斜四边形**。

所以那张 PNG 对应的既不是「文件原始模式」，也不是我们单独注入的 31。
它很可能是**菜单里某个具体项**在当前文件上被选中后的状态——而菜单是自绘列表，
滚动位置随当前项变化，鼠标坐标点选很容易落到相邻项（本次调试里已多次发生）。
在拿到「截图时下拉里到底是哪一项」之前，不能把 31 直接当成菜单 KYUSHU。

## 2. 维护者确认后的结论

维护者确认：

1. 截 `HDFA43_KYUSHU_IMGP1157.png` 时，PDCU 下拉里选的就是 **KYUSHU**；
2. `IMGP1157.DNG` 是**机内就选了 KYUSHU** 拍的。

在这个前提下，最合理的解释是：

- 43 的文件里带着**相机算好的 KYUSHU 参数**；在 PDCU 里选 KYUSHU 时，这套参数在，
  所以得到正确的斜四边形；
- 77 的文件不是机内 KYUSHU，文件里没有这套参数；同一个菜单 KYUSHU 只能套
  PDCU 自己的通用/默认预设，于是颜色和雷达图都不对；
- 镜头只是「能不能机内拍 KYUSHU」的间接条件，真正决定画面的是
  **文件里有没有相机那套 KYUSHU 参数**，而不是镜头标识本身（第 1.1 节已用换镜头验证）。

因此「只有 HD FA 43 正常」= 只有它带着正确的 KYUSHU 参数，不是 PDCU 对镜头区别对待。

## 3. 修复方向

1. **参数移植**：从 43 的 DNG 里找出相机写入的 KYUSHU 参数块，写进其它 DNG，
   再在 PDCU 里选 KYUSHU 验证。
   - 已确认的第一个入口：PentaxDng 私有 IFD `0x0200`（8 字节）。
     43 是 `00 04 00 04 00 04 00 04`，77 是 `00 01 00 01 00 01 00 01`；
     只把这 8 字节写进 77 的 DNG，画面就明显变化（`.tmp/p1194_0200.png`），
     说明它确实是相机自定义影像参数的一部分。
   - 还缺颜色矩阵/曲线那一块（候选：`0x0201`、`0x0216`、`0x021f`、`0x024e`）；
     只移植 `0x0200+0x0216+0x021f` 时雷达仍是五边形，没有回到 KYUSHU 的斜四边形。
2. **补 PDCU 预设**：找到菜单 KYUSHU（0x1F）参数模板的填充点，把缺失的相机侧参数补进去。
3. **最快拿到准确差异**：同场景、同镜头，KYUSHU 与另一模式各拍一张 DNG，
   就能把 KYUSHU 的变换从场景/WB 中分离出来，直接得到要移植的参数。

## 7. 2026-10-23 突破：KYUSHU 数据就在 DNGPrivateData 里

用第二张机内 KYUSHU 样片 `IMGP0110.DNG`（HD DA 21mm）做对照后确认：

- 1157（43mm）与 0110（21mm）虽然镜头、场景、年份都不同，PDCU 里都显示**斜四边形**（KYUSHU 特征）；
- 1194（77mm，非 KYUSHU）是六边形；
- 三张 DNG 的 `DNGPrivateData` 块**长度完全相同（195,676 字节，文件偏移 1022）**。

### 块级移植

把 1157 的 `DNGPrivateData` 块整块写进 1194（保留 1194 的 raw 像素），
PDCU 立刻变成 KYUSHU：雷达图斜四边形、红色/暖色表现出现。

二分定位（每次只把 1157 的一段字节写进 1194）：

| 写入范围 | 结果 |
|---|---|
| 整块 195,676 B | KYUSHU（斜四边形） |
| 前 1/2（97,838 B） | KYUSHU |
| 前 1/4（48,919 B） | KYUSHU |
| 前 1/8（24,459 B） | KYUSHU |
| 前 1/16（12,229 B） | 六边形（不够） |
| 前 1/16 + `0x33C3..0x49A6` | KYUSHU |
| 前 1/16 + `0x33C3..0x3EB5` | **KYUSHU** |
| 前 1/16 + `0x3782..0x3802`（128 B） | 六边形（不够） |

`0x33C3..0x3EB5` 落在私有 IFD 的 tag **`0x021f`** 里（`0x3782` 起，4,984 字节 ≈ 17³×3 + 71 字节，
像一个 3D LUT + 头部）。前 1/16 里则包含 IFD 本身、`0x0200/0x0206–0x0209/0x0216` 等。

### 两张 KYUSHU 样片共同的标记

按 tag 比较，1157 与 0110 完全相同、而 1194 不同的是：

| tag | 1157 = 0110 | 1194 |
|---|---|---|
| `0x0014` | 21（0x15） | 12（0x0C） |
| `0x0016` | 50（0x32） | 40（0x28） |
| `0x0200` | 1024,1024,1024,1024 | 256×4 |
| `0x024c` | 1024×4 | 256×4 |

但只移植这 4 个 tag 不足以复现 KYUSHU（雷达仍是六边形），还需要 `0x021f` 里的数据。

### 当前移植的副作用

整块/大段移植会同时带入 1157 的**白平衡/影调**，1194 会偏橙。也就是说：
“KYUSHU 模式”已经在文件里找到了，但还没把「模式数据」和「这张照片的场景数据」分开。
下一步是在 `0x3782..0x3EB5` 内继续二分（约 4 次可见底），找出只负责 KYUSHU 颜色特征的最小字段，
再做成「只写 KYUSHU 模式、不动目标照片 WB/影调」的工具。

### 7.1 当前可用的移植配方

在 1194 上（像素不动）写入 1157 的这两段，PDCU 就会进入 KYUSHU 状态（斜四边形）：

```
[0x03FE, 0x33C3)          私有 IFD + 0x0200/0x0201/0x0206–0x0209/0x0216
[0x33C3, 0x3EB5)          0x021f 内的 2.8 KB 结构
```

- 只写前 1/16（0x3FE..0x33C3）→ 六边形；
- 只写 `0x33C3..0x3EB5` → 六边形；
- 两段同时写 → KYUSHU；
- 只写 `0x3782..0x3B1C` 或 `0x3B1C..0x3EB5`（各一半）→ 六边形（结构跨过中点，不能拆）；
- 4 个标记 tag + `0x3782..0x3EB5`、或再加 `0x0209`，都不够；
- 直接清零 `0x3782..0x3EB5` 也不够。

### 7.2 副作用与边界

- 移植后 1194 会带上**提供者（1157 或 0110）的影调/白平衡**，画面偏橙。
  即：这 2.8 KB 结构不是“模式开关”，而是相机按这张照片算出来的**色调/颜色数据**；
  换一张场景就得重新算，不能直接搬。
- 这解释了为什么 PDCU 菜单里的 KYUSHU 对非 KYUSHU 文件无效：
  **PDCU 5.10.2.2 没有内置 SE 的完整参数表，它依赖文件里相机写好的这套数据。**
  补丁只放开了菜单，没法凭空生成缺失的数据。

### 7.3 如果要“任意图都能套 KYUSHU”

只有两条路：

1. **近似**：拿一张机内 KYUSHU 的 DNG 当供体，把上面两段写进目标（可用，但会带入供体的影调/白平衡）；
2. **精确**：把 `0x33C3..0x3EB5` + 前 1/16 里那套相机计算规则逆出来（属于相机引擎级工作，
   和本仓库的固件移植是同一条线），才能在任意 RAW 上重算 KYUSHU。

### 7.4 剥离“偏色”的尝试（2026-10-23 续）

目标：保留 KYUSHU 模式，但不带入供体的影调/白平衡。

| 尝试 | 结果 |
|---|---|
| 正常移植（前缀 + `0x33C3..0x3EB5`） | KYUSHU 斜四边形，画面偏橙 |
| 移植后保留目标自己的 WB（`0x0201`） | 雷达变成细菱形，仍偏橙 |
| 移植后保留目标自己的 `0x0209` 曲线 | 同上，仍偏橙 |
| 改用 0110（DA21，室内 KYUSHU）当供体 | 仍偏橙 |

结论：偏色不是供体的白平衡或场景造成的，而是这套数据**本身**在目标 RAW 上作用的结果。
`0x021f` 的 4,984 字节开头是若干 signed 16-bit 参数对（1157：`324,-28,0,0,147,-1,…`；
1194：`310,-5,0,0,-48,0,…`），不是简单的单调曲线，也不是 17³ 3D LUT（17³×3 会到 14,739 B）。
它更像相机按当前影像算出的**颜色/影调系数表**，和模式、白平衡、镜头一起耦合。

这意味着：**只靠 tag/字节移植，无法既拿到 KYUSHU 模式、又不带供体偏色。**
要做到“任意图、不偏色”的 KYUSHU，必须在目标 RAW 上**重算**这套系数——
也就是把相机端的计算规则逆出来（固件/引擎级），而不是在 PDCU 的文件层解决。

## 8. K-3 III v2.20 固件检查（2026-10-23）

文件：`firmware/k3III_v220/fwdc233b.bin`（35,106,716 B）

- 头部明文：`PENTAX\0K-3 Mark III\0RICOH IMAGING COMPANY, LTD.\0`；
- 4 KiB 块熵中位数 **7.79**、p90 **7.94**，正文是打包/编码流；
- 字符串被 1–2 字节 token 打断：
  - `FuyunowD$`（Fuyuno + token）
  - `uben`（Harubeni 的尾巴）
  - `A:\Resource\Font\LE_JP.bin` 中间也插了 token
- 没有明文 `KYUSHU/HARUBENI/KATEN/FUYUNO`；`Gold` 能以完整 ASCII 出现，属于个别对齐情况；
- 全文件搜索 DNG `0x021f` 的头部字节序列（1157/1194）**0 命中**；
- 连 KF 那种 28 KB 明文升级 agent（`SD Writers`/`Flash Writer`）也没有，K-3 III 的正文从很早就进入打包流；
- 文件里没有解码器（`P9dec`/`Unpack` 等均无）。

结论：**K-3 III 与 KF/K-1 同属“打包流”，且这次连明文引导段都没有；
不解包就无法拿到 SE 的参数/计算代码。** 这与 KF 的结论一致，解码器应在 ROM 或相机运行态。

### DNG 语料旁证

把 Desktop 上多张带 DB `quality` 的 DNG 对齐看 `0x021f` 头部：

| 文件 | DB quality | 0x021f 头部 |
|---|---|---|
| IMGP0110（机内 KYUSHU，DA21） | 31 | 全 0 |
| IMGP1157（机内 KYUSHU，43） | 31 | `44 01 e4 ff …` |
| IMGP1146 | 31 | `3d 01 f0 ff …` |
| IMGP1190 | 31 | `7d 00 f0 ff …` |
| IMGP1194（非 KYUSHU，77） | 31 | `36 01 fb ff …` |
| IMGP0306 | 33 | 全 0 |
| IMGP2204 | 30 | 全 0 |

同为 quality 31 的 KYUSHU 文件里，0110 是全 0、1157 是密集值——说明 `0x021f` **不是按模式固定的表**，
而是随影像/场景变化的数据；它和模式、白平衡、镜头一起耦合，不能单靠“找模式表”解决。
